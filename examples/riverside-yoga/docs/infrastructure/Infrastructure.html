How it works

Members, mostly from their phone, instructors and the front desk all use one Next.js web application on Vercel, with functions in an EU region. Vercel keeps no data: it reads and writes Supabase on every request, and caches only the public schedule for a minute.

Supabase, in an EU region, holds the database, sign-in and scheduled jobs. Booking a class is one database transaction that checks capacity, the member's credits and the 12-hour rule together: two people can never take the last spot, and a credit is never spent twice.

Stripe takes every payment; the studio never sees card numbers. When a payment succeeds, Stripe calls a webhook and the credits appear in the member's account. Emails leave from the studio's own domain.

Members pay on Stripe's own page and come back: card data never passes through our code. The webhook, not the browser, is what adds credits, so closing the page during payment loses nothing.

The rules that hold it together

  • Data stays in Europe. Database and functions in an EU region; Vercel, Stripe and the email service receive only what they need and are listed as sub-processors.
  • The database enforces the booking rules. Capacity, credits and the 12-hour window are checked in one transaction, not in the interface.
  • Stripe decides, the database records. Credits and memberships change only on Stripe's webhook, never from the browser.
  • Members see only their own data. Row-level rules on every table; instructors see the attendees of their own classes only.
  • Accounts belong to the studio. The studio opens every service and invites us as administrators.
